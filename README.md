# Chirpy Server

Chirpy Server is a REST API for a small social platform where users can create, view, and delete short posts called **chirps**.

The project is built with **TypeScript**, **Express**, **PostgreSQL**, and **Drizzle ORM**. It includes user authentication with JWT access tokens and refresh tokens, password hashing with Argon2, database migrations, protected endpoints, and a webhook for upgrading users to Chirpy Red.

> **Project note:** This project was built as part of the Boot.dev Chirpy course. It is primarily a learning project focused on building a production-style HTTP API with TypeScript, authentication, PostgreSQL, and database tooling.

## Features

- User registration and login
- Secure password hashing using Argon2
- JWT-based authentication
- Refresh-token authentication and revocation
- User profile updates
- Create, list, retrieve, and delete chirps
- Chirp length validation with a 140-character limit
- Automatic filtering of specified words in chirps
- Optional filtering of chirps by author
- Ascending and descending chirp sorting
- Chirpy Red user upgrades through a webhook
- PostgreSQL persistence
- Drizzle ORM database schema and migrations
- Health/readiness endpoint
- Request metrics endpoint
- Development-only database reset endpoint
- Automated tests with Vitest
- Centralized HTTP error handling

## Prerequisites

Before running the project, make sure you have:

- Node.js installed
- npm installed
- PostgreSQL running locally or an accessible PostgreSQL database

The project expects a PostgreSQL database connection through the `DB_URL` environment variable.

## Installation

Clone the repository:

```bash
git clone https://github.com/Alaa-M-Saleh/ChirpyServer.git
cd ChirpyServer
```

Install dependencies:

```bash
npm install
```

## Environment Variables

Create a `.env` file in the project root.

```env
DB_URL="postgres://postgres:postgres@localhost:5432/chirpy?sslmode=disable"
PORT=8080
PLATFORM=dev
JWT_SECRET="your-jwt-secret"
POLKA_KEY="your-polka-api-key"
```

The application requires the following variables:

| Variable | Description |
|---|---|
| `DB_URL` | PostgreSQL connection URL |
| `PORT` | Port used by the API server |
| `PLATFORM` | Current platform/environment. The reset endpoint is restricted to `dev` |
| `JWT_SECRET` | Secret used to sign and validate JWT access tokens |
| `POLKA_KEY` | API key used to authenticate Polka webhook requests |

**Never commit your real `.env` file or expose your JWT secret/API keys publicly.**

## Users

### Create a User

#### `POST /api/users`

Creates a new user.

**Request**

```json
{
  "email": "user@example.com",
  "password": "password"
}
```

**Response — `201 Created`**

```json
{
  "id": "user-uuid",
  "createdAt": "timestamp",
  "updatedAt": "timestamp",
  "email": "user@example.com",
  "isChirpyRed": false
}
```

Passwords are hashed with Argon2 before being stored.

### Login

#### `POST /api/login`

Authenticates a user and returns an access token and refresh token.

**Request**

```json
{
  "email": "user@example.com",
  "password": "password"
}
```

An optional `expiresInSeconds` field can be supplied. The access-token lifetime is capped at one hour.

**Response — `200 OK`**

```json
{
  "id": "user-uuid",
  "createdAt": "timestamp",
  "updatedAt": "timestamp",
  "email": "user@example.com",
  "isChirpyRed": false,
  "token": "jwt-access-token",
  "refreshToken": "refresh-token"
}
```

### Refresh Access Token

#### `POST /api/refresh`

Creates a new access token using a valid refresh token.

**Header**

```http
Authorization: Bearer <refresh-token>
```

**Response — `200 OK`**

```json
{
  "token": "jwt-access-token"
}
```

Refresh tokens are stored in the database and have an expiration time. Revoked or expired refresh tokens are rejected.

### Revoke Refresh Token

#### `POST /api/revoke`

Revokes a refresh token.

**Header**

```http
Authorization: Bearer <refresh-token>
```

**Response**

```text
204 No Content
```

### Update User

#### `PUT /api/users`

Updates the authenticated user's email and password.

**Header**

```http
Authorization: Bearer <access-token>
```

**Request**

```json
{
  "email": "new@example.com",
  "password": "new-password"
}
```

**Response — `200 OK`**

```json
{
  "id": "user-uuid",
  "createdAt": "timestamp",
  "updatedAt": "timestamp",
  "email": "new@example.com",
  "isChirpyRed": false
}
```

## Chirps

A chirp is a short post with a maximum length of **140 characters**.

### Create a Chirp

#### `POST /api/chirps`

Creates a chirp for the authenticated user.

**Header**

```http
Authorization: Bearer <access-token>
```

**Request**

```json
{
  "body": "Hello from Chirpy!"
}
```

The API replaces the following words with `****` when they appear as individual space-separated words:

- `kerfuffle`
- `sharbert`
- `fornax`

**Response — `201 Created`**

```json
{
  "id": "chirp-uuid",
  "createdAt": "timestamp",
  "updatedAt": "timestamp",
  "body": "Hello from Chirpy!",
  "userId": "user-uuid"
}
```

### Get Chirps

#### `GET /api/chirps`

Returns chirps.

Optional query parameters:

| Parameter | Description |
|---|---|
| `authorId` | Returns chirps belonging to a specific user |
| `sort` | Use `desc` for newest-first ordering; otherwise chirps are returned oldest-first |

**Examples**

```http
GET /api/chirps
```

```http
GET /api/chirps?authorId=<user-uuid>
```

```http
GET /api/chirps?sort=desc
```

```http
GET /api/chirps?authorId=<user-uuid>&sort=desc
```

### Get a Chirp

#### `GET /api/chirps/:chirpId`

Returns a single chirp by its UUID.

**Example**

```http
GET /api/chirps/123e4567-e89b-12d3-a456-426614174000
```

**Response — `200 OK`**

```json
{
  "id": "chirp-uuid",
  "createdAt": "timestamp",
  "updatedAt": "timestamp",
  "body": "Hello from Chirpy!",
  "userId": "user-uuid"
}
```

### Delete a Chirp

#### `DELETE /api/chirps/:chirpId`

Deletes a chirp.

**Header**

```http
Authorization: Bearer <access-token>
```

Only the user who created the chirp can delete it.

**Response**

```text
204 No Content
```

## Polka Webhook

### Upgrade a User to Chirpy Red

#### `POST /api/polka/webhooks`

Handles Polka webhook events.

The endpoint expects an API key in the `Authorization` header using the `ApiKey` scheme:

```http
Authorization: ApiKey <polka-api-key>
```

For a `user.upgraded` event, the request body contains the user's ID:

```json
{
  "event": "user.upgraded",
  "data": {
    "userId": "user-uuid"
  }
}
```

A successful upgrade sets the user's `isChirpyRed` status to `true`.

Events other than `user.upgraded` are acknowledged without performing an upgrade.

## Authentication

Chirpy uses two types of tokens:

### Access Tokens

Access tokens are JWTs containing the authenticated user's ID.

They are sent using:

```http
Authorization: Bearer <access-token>
```

Access tokens have a maximum lifetime of one hour.

### Refresh Tokens

Refresh tokens are cryptographically generated random values and are stored in PostgreSQL.

They:

- Have a 60-day expiration period
- Can be revoked
- Are checked for expiration before being used
- Can be exchanged for a new one-hour access token

### Password Security

Passwords are never stored directly. Chirpy hashes passwords using **Argon2** and verifies submitted passwords against the stored hashes.

## Database Model

The application uses three main database tables.

### `users`

Stores user accounts.

```text
id
created_at
updated_at
email
hashed_password
is_chirpy_red
```

### `chirps`

Stores posts created by users.

```text
id
created_at
updated_at
body
user_id
```

Each chirp belongs to a user through a foreign-key relationship. Deleting a user cascades to their chirps.

### `refresh_tokens`

Stores refresh-token information.

```text
token
created_at
updated_at
user_id
expires_at
revoked_at
```

Refresh tokens are associated with users and support expiration and revocation.
